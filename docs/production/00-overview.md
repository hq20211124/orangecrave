# 生产就绪总览

> 目标读者：完全没有 DevOps 经验的工程师。照着做，每一步都有命令和验证方法。

## 这套系统现在是什么状态

OrangeCrave 后台已经完成了三批架构改造，具备了大型系统的「形状」：

- 缓存 / 分布式锁 / 限流 / 库存预扣 — 有抽象层，可切 Redis 实现
- 消息队列 — 内嵌同步模式 + Redis Stream 异步模式，可切换
- 对象存储 — Local / S3 抽象，可切换
- 幂等 / 事务 / 状态机 — 核心链路有保护
- 154 个自动化测试全绿

**但「形状对了」不等于「能扛生产流量」。** 从演示到生产，差的是以下 8 个领域。

## 实施顺序

不要试图一次全做。按依赖关系和风险从低到高排序：

```
第一阶段（基础设施）          第二阶段（质量保障）           第三阶段（生产就绪）
┌─────────────────┐      ┌─────────────────┐      ┌─────────────────┐
│ 1. 部署容器化    │      │ 4. 数据库高可用  │      │ 7. 真实渠道集成  │
│ 2. 可观测接入    │  →   │ 5. 压测验证     │  →   │ 8. 运维体系      │
│ 3. 安全加固      │      │ 6. 容灾预案     │      │                 │
└─────────────────┘      └─────────────────┘      └─────────────────┘
  约 2 周                  约 2 周                    约 2~4 周
```

### 为什么是这个顺序

1. **部署先行** — 没有容器化，后面的 K8s、多可用区都无从谈起
2. **可观测紧随其后** — 没有监控，做安全加固和压测时你什么都看不到
3. **安全在压测之前** — 压测会暴露安全短板（限流是否生效、注入是否被拦截），先补安全再压
4. **数据库高可用** — 单实例挂了整个系统就停了，这是最大单点风险
5. **压测在容灾之前** — 先知道单点能扛多少，才知道容灾需要多少冗余
6. **容灾** — 有了容量数据，才能合理规划多可用区
7. **集成放后面** — 真实支付/物流有合规门槛，先把内部系统搞稳
8. **运维体系贯穿始终** — 但从第一天就要定义 SLO，否则后面补的时候会发现没人知道「系统应该多好」

## 验收标准

每完成一个领域，用以下标准自验：

| 领域 | 验收标准 |
|------|----------|
| 部署 | `kubectl apply` 一条命令拉起完整环境；滚动更新不丢请求 |
| 可观测 | Grafana 能看到 QPS/延迟/错误率；日志能按 traceId 串联 |
| 安全 | 敏感配置不落盘、不走 Git；API 有认证+限流+WAF |
| 数据库 | 主从延迟 < 1s；备份恢复演练 RTO < 30min，RPO < 5min |
| 压测 | 秒杀接口支撑目标 QPS 的 3 倍余量，错误率 < 0.1% |
| 容灾 | 单可用区宕机，30s 内自动切换到健康区域 |
| 集成 | 支付/退款/物流全链路回调可达，对账差异 < 0.01% |
| 运维 | 告警到人，5min 内响应；SLO 达标率 > 99.9% |

## 怎么开始

如果你是第一次接触 DevOps，按这个路径走：

1. 先读 [01-deployment](01-deployment.md)，把系统容器化
2. 再读 [02-observability](02-observability.md)，把监控接起来
3. 然后按顺序读剩下的文档

**不要跳步。** 每一步都依赖前面的基础。
