# 03 · 订单与生产

## 1. 订单模型

### 1.1 订单类型

| 值 | 类型 | 说明 |
|---|---|---|
| 1 | 普通订单 | 用户自购自收 |
| 2 | **打样单** | 用户印一份看效果 |
| 3 | **无料领取单** | 凭分享码领取，作者已付制品费 |
| 4 | 现货订单 | 有实物库存 |

### 1.2 三种付款结构

| 场景 | 付款人 | 付什么 |
|---|---|---|
| 普通订单 | 下单人 | 商品费 + 邮费 |
| **普通分享** | 领取者 | 商品费 + 邮费 |
| **无料分享** | **分享者**付商品费 / **领取者**付邮费 |
| 拼团订单 | 团员各自 | 拼团价 |

> **`payer_user_id` 字段存在的意义**：无料场景下付款人与下单人分离。系统所有金额、退款、对账逻辑必须认 `payer_user_id`，不能默认 `user_id`。这是本系统与常规电商最容易踩坑的差异点。

### 1.3 一单多件与图槽位

订单主表 `oms_order` + 明细 `oms_order_item` + 图片 `oms_order_image` 三层。

一个明细下可挂**多个「图 + 份数」对**，同时覆盖两种真实需求：

- 20 张各不相同的图（套卡）
- 1 张图印 20 份（送人 / 换卡）

**支持购物车混单**：小卡 + 手机壳 + 卡册可一起下单，运费**按整单**计算。

混单实现口径（v1 已落地）：

- 入参 `items[]` 每行一个 `{skuId, qty, craftIds, activityId, images[]}`；不传 `items` 时按单行简写字段（`skuId/qty/craftIds/activityId/images`）组装一行，老调用方零改动。
- **逐行计价**（各自的活动价、工艺加价、起订量与递增量校验，见 04 篇 §2.3），商品金额求和；优惠券与运费按**整单**：券在券前总额上抵扣，运费模板取**第一行**的，基数与件数用整单。
- **秒杀按行**：每行抢自己活动的独立配额（`oms_order_item.activity_id` 落行），取消 / 退款按活动聚合归还；整单 `oms_order.activity_id` 取第一行带活动的，仅用于展示与统计。
- 分享码核销套数按**整单件数**计；无料分享置零商品费的行为不变。
- 每行一条 `oms_order_item`，图槽位挂各自行的 `order_item_id` 下。

## 2. 订单状态机

### 2.1 状态定义

自印是**真印刷**，只做「付款 → 发货」两个状态不够——订单在车间里的过程必须可见，否则客服答不了「我的小卡做到哪了」，而这是饭圈用户最常问的问题。

| 值 | 状态 | 说明 |
|---|---|---|
| 0 | 待付款 | 已下单未支付 |
| 1 | 待成团 | 拼团单专有，等待人数凑齐 |
| 2 | **待审核** | 定制图审核中 |
| 3 | **待生产** | 审核通过，等待派单 |
| 4 | **生产中** | 车间制作中 |
| 5 | **质检** | 制作完成，质检 |
| 6 | 待发货 | 质检通过 |
| 7 | 已发货 | 在途 |
| 8 | 已完成 | 签收 / 自动确认 |
| 9 | 已取消 | 未付款超时或主动取消 |
| 10 | 售后中 | 有未结售后单 |
| 11 | 已退款 | 退款完成 |

### 2.2 主流程

```
待付款 ──支付──> [待成团] ──成团──> 待审核 ──通过──> 待生产 ──派单──> 生产中
                      │                                        │
                   未成团↓                                  ──质检──> 待发货 ──发货──> 已发货 ──签收──> 已完成
                   已取消(退款)                                              │
                                                                         售后中 ──> 已退款
```

- **方括号 `[待成团]`** 仅拼团单经过，普通单支付后直接进「待审核」
- **审核驳回** → 回到用户端「待修改」，订单挂起

### 2.3 流转表（配置化）

状态机**做成配置化的转换表**，而不是散落各处的 `if-else`。守卫条件由表生成。

| from | to | 触发 | 守卫条件 | 副作用 |
|---|---|---|---|---|
| 待付款 | 待审核 | 支付回调 | `status = 待付款` | 记录 `pay_time` |
| 待付款 | 待成团 | 支付回调 | 订单有 `group_id` | 团人数 +1 |
| 待付款 | 已取消 | **超时任务** | `status = 待付款` 且 `expire_time < now` | **还库存 + 返优惠券** |
| 待付款 | 已取消 | 用户取消 | `status = 待付款` | 同上 |
| 待成团 | 待审核 | **成团** | 团 `current_size >= target_size` | 开团其余成员转待审核 |
| 待成团 | 已取消 | **团超时** | `status = 待成团` | **自动退款** |
| 待审核 | 待生产 | 审核通过 | `status = 待审核` | 生成生产工单 |
| 待审核 | 已取消 | 审核驳回 | `status = 待审核` | 通知用户修改 |
| 待生产 | 生产中 | 派单 | `status = 待生产` | 写 MES 工单号 |
| 生产中 | 质检 | 生产完成 | `status = 生产中` | — |
| 质检 | 待发货 | 质检通过 | `status = 质检` | — |
| 待发货 | 已发货 | 录入运单 | `status = 待发货` | 可回退 |
| 已发货 | 已完成 | 签收 / **超时** | `status = 已发货` 且超时 10 天 | 记录 `confirm_time` |
| 已发货 | 售后中 | 申请售后 | 在售后窗口内 | — |
| 售后中 | 已退款 | 售后通过 | `status = 售后中` | **退款流水** |

### 2.4 并发正确性

**绝不「先查再改」**。所有流转统一：

```sql
UPDATE oms_order SET status = #{to}
WHERE id = #{id} AND status = #{from};
-- 影响行数 == 1 才执行副作用
```

- 重复触发：第二次匹配 0 行，无操作
- 取消 vs 支付竞态：先提交者赢，输的一方走退款或放弃分支

**副作用必须在同一事务内**（还库存、返券、写流水）。

### 2.5 状态与延迟任务绑定

| 状态 | 延迟任务 | 触发后 |
|---|---|---|
| 待付款 | 30 分钟（可配） | → 已取消 |
| 待成团 | 团 `expire_time`（24h） | → 已取消 + 退款 |
| 待发货 | 72 小时（可配） | 仅告警，不改状态 |
| 已发货 | 10 天（可配） | → 已完成 |
| 售后中 | 售后超时（可配） | 自动关闭 |

机制见 `00` 篇第 5 节（DelayQueue + 启动重建 + 兜底扫描）。

### 2.6 秒杀下单的削峰入口

秒杀是本项目唯一的高并发入口，其余下单仍走同步的 `POST /client-api/oms/order/submit`——没有峰值压力的入口引入异步只会徒增复杂度。秒杀单走另一条链：

```
① 受理   POST /client-api/oms/order/seckill
         限流（Redis + Lua 令牌桶，超限回 code=429）
         → 预扣配额（04 篇 §3.3，内存闸门先挡，库层条件 UPDATE 兜底）
         → 发 requestId、写「QUEUED」→ 投递消息 → 立即返回
② 消费   MessageListener 在后台线程跑完整的 OrderService.submit（落库 / 扣库存 / 写明细 / 挂延迟任务）
         → 结果写回同一 requestId
③ 轮询   GET /client-api/oms/order/seckill/result/{requestId}
         → QUEUED 继续 / SUCCESS(带 orderId) / FAILED(带可展示原因)
```

契约要点：

- **只在受理与消费之间异步**。消费侧执行的就是那一个同步 `submit`，状态机、幂等、扣减全部沿用既有路径，削峰不引入第二套下单逻辑。
- **结果有 TTL**（10 分钟，覆盖轮询窗口）；`requestId` 同时是幂等键，消息重投不会产生第二个订单。
- **通道可替换**：`MessagePublisher` / `MessageListener` 之下当前是 Redis Stream（消息落地、消费者组、可事后补处理），换 RocketMQ / Kafka 时业务侧不改。开关关闭时退回同步直投，功能不变、只是没有异步。
- **限流之后仍有兜底**：入口被限流压低后，万一仍未压住，`ioExecutor` 的 `CallerRunsPolicy`（队列容量 0）会让提交线程亲自执行，而不是抛拒绝丢结果。

## 3. 退款规则

### 3.1 规则结论

以下为调研得到的业务规则，用本系统自己的表述记录（原文摘录已移除）：

- 定制类商品不适用七天无理由退货；一旦交付生产即不可退。
- 付款后 4 小时内可自行申请改单或退款，超时走客服工单。
- 因收件人原因（超时未取件、地址不详等）造成的退回，需补运费后重新寄出。

### 3.2 规则表

| 时点 | 用户能否退 | 说明 |
|---|---|---|
| 未付款 | 可取消 | 自由取消 |
| 付款后 **4 小时内** | **可申请退款** | 退款窗口 |
| 4 小时后 ~ 进生产前 | **不可自助退**，可提工单 | 客服判断 |
| **进入生产后** | **不可退** | 定制类印刷后即为废品 |
| 已发货 | 不可退 | 定制品无 7 天无理由 |
| 质量问题 / 色差 | **走售后** | 独立通道 |

### 3.3 管理员强制退款

- 需要 `order:refund:force` 权限
- **必须记录操作日志快照**（谁、何时、为何、金额）
- **财务角色复核**（两段式）
- 走独立入口 `/admin-api/oms/order/{id}/force-refund`

### 3.4 按明细退

支持 `oms_aftersale.order_item_id` 精确到明细行。一单多件时只退其中一件。

### 3.5 退款通道

**原路退回微信支付**。退款渠道抽 `RefundAdapter` 接口，v1 走桩实现。

### 3.6 退款流水

所有退款写入 `fin_refund_ledger`，**不直接冲减销售额**。对账时以流水为准。

## 4. 生产与 MES 对接

### 4.1 定位

**车间有 MES**，因此后台**不重造生产执行**：

- 后台**不建**排产、工序、机台、质检记录等 MES 职责的表
- 后台只存 **MES 工单号** + **状态映射** + **对用户展示的粗粒度进度**

> 顾客端已有工厂日历相关端点（`factory/calendar/delayed`、`batch/expected-delivery`），说明工厂对接是真实存在的，且顾客端已在用。

### 4.2 ProductionAdapter

```java
public interface ProductionAdapter {
    String createWorkOrder(ProductionOrderDTO dto);   // 返回 MES 工单号
    ProductionStatus queryStatus(String workOrderNo);
    void syncStatus(String workOrderNo);
}
```

| 阶段 | 实现 |
|---|---|
| v1 | `ManualProductionAdapter` —— 仓管手工录入工单号、手工推进状态 |
| 将来 | `MesProductionAdapter` —— 调 MES API，状态回调 |

**迁移时业务代码不动**，只换实现类。

### 4.3 状态映射

MES 术语与用户可读文案分离：

| MES 状态（示例） | 后台状态 | 对用户展示 |
|---|---|---|
| 已开料 / 已上机 | 生产中 | 「正在制作」 |
| 待后道 | 生产中 | 「正在制作」 |
| 裱纸中 | 生产中 | 「正在制作」 |
| 品检 | 质检 | 「质检中」 |

> 加这层映射的原因：MES 是给车间看的，术语按工序走；把「已上机裱纸」直接怼给用户看是灾难。

### 4.4 生产工单

| 字段 | 说明 |
|---|---|
| `order_id` | 关联订单 |
| `work_order_no` | **MES 工单号** |
| `status` | 待生产 / 生产中 / 质检 / 完工 |
| `craft_list` | 工艺清单（从 SKU 带出，如白墨/烫金/覆膜） |
| `expected_delivery` | **预计交期**（来自工厂日历） |
| `sync_time` | 最近同步时间 |

### 4.5 不做的事

| 不做 | 原因 |
|---|---|
| 拼版引擎 | **服务端已有**（`goods` 模块含 `multiMergeImg`） |
| 排产 / 机台 | MES 职责 |
| 材料损耗核算 | 成本会计，二期 |
| 完整 MES | 规模不匹配 |

## 6. 售后

### 6.1 类型

| 值 | 类型 | 说明 |
|---|---|---|
| 1 | 退款 | 仅退钱 |
| 2 | 退货退款 | **定制品基本不适用** |
| 3 | **色差** | 自印高频问题，v1 只做类型与文案 |
| 4 | 其他 | 质量问题等 |

### 6.2 流程

```
用户提交 ──> 待审 ──客服审核──> 通过 ──> 退款(写流水) ──> 完成
                    │
                    └──> 驳回（必填理由）──> 通知用户
```

### 6.3 与工单的关系

- **售后** = 有订单、要退钱 → 走 `oms_aftersale`
- **客服工单** = 咨询、投诉、无订单 → 走 `svc_ticket`

两者可能关联（用户先提工单，客服转为售后），但不合并。

## 7. 特殊订单流程

### 7.1 拼团流程

```
用户开团/参团 ──支付(拼团价)──> 待成团
                                  │
                    ┌─────────────┴─────────────┐
                  满员                        24h 到期未满
                    │                            │
                 已成团                        拼团失败
                    │                            │
              全员转待审核                 全员自动退款
```

- **3 人成团 · 24 小时**
- 人数与时长**活动可配**，默认照此
- **拼团价与优惠券互斥**
- **模拟成团**：到期未满员时注入虚拟团员成团，避免退款。**做成开关，默认关闭**

**成团判定与退款并发**：团的 `current_size` 递增和成团判定都必须走条件 UPDATE，避免「第 3 人支付」与「到期任务」同时触发导致重复。

### 7.2 打样流程

```
作者选择商品 ──> 打样下单(收费) ──> 生产 ──> 发货 ──> 作者收到实物确认效果
                                                          │
                                              打样完成 ──> 解锁分享码发放
```

- **打样 = 作者自己印一份看效果**，不是企业打样给企业看
- **真发货**
- **按成本价收费**【推断】
- **不进销售统计**（是成本不是收入），但进成本账【推断】
- **是发放分享码的前置条件**
- 团长 / 摊主有**专属打样券**（认证通过后解锁）

> 【待确认】打样的具体收费方式（成本价？固定价？免运费？）代码中无法判定。

### 7.3 无料分享流程

```
作者已打样 ──> 创建无料分享 ──> author 支付制品费(进平台) ──> 生成分享码
                                                              │
                                              领取者输入码 ──> 下单，仅付邮费
                                                              │
                                              核销 ──> prepay_used += 
                                                              │
                                          码失效/超量/作品封禁
                                                              │
                                    退未核销余额 ──> prepay_refunded += 
```

**关键点**：

1. 分享者**创建时即付款**
2. 领取者**只付邮费**
3. 分享码有**可下单套数上限**与**有效期**
4. **失效三因**：超有效期 / 作品被封禁 / 超最大下单数量
5. 预付金额拆为「已核销 / 未核销 / 已退」

**退款规则**：退未核销余额，已核销不退。

> 【待确认】是否能退取决于 `freeShareConfig` 中的价格档位。**默认实现为可退**。

### 7.4 合集流程

- **2–10 个作品**组成合集
- 两种模式：**合并下单**（`合集需合并下单`）或**单个下单**（`合集可单个下单`）
- 合并下单时运费按整单算

## 8. 订单快照原则

订单一旦创建，以下内容**全部固化，不随源数据变化**：

| 快照 | 字段 |
|---|---|
| **收货地址** | `receiver_snapshot` (json) |
| 商品信息 | `goods_name` / `sku_spec` / `image` |
| 价格 | `unit_price` / `total_price` |
| 工艺 | `craft_snapshot` (json) |
| 计价参数 | `pricing_snapshot` (json) |
| 图片 | 从作品图槽位**复制**到 `oms_order_image` |

> **地址快照的理由**：用户随时可改地址。若订单持外键，改地址会污染历史订单——已发货订单显示新地址，对账与客服都出事。

## 9. 需要特别注意的三处

| 处 | 坑 | 对策 |
|---|---|---|
| **付款人 ≠ 下单人** | 无料场景下所有金额逻辑认 `user_id` 会错 | 一律用 `payer_user_id` |
| **成团 vs 到期竞态** | 第 3 人付款与 24h 到期任务可能同时跑 | 条件 UPDATE + `tsk_delay_log` 唯一键 |
| **打样单混入销售统计** | 打样不是售卖行为 | `order_type = 2` 在统计中排除 |

## 10. 适配器与桩实现契约（v1）

v1 对四类外部依赖走**适配器 + 桩**。桩行为必须在实现前定死，否则状态机无法被真实验证：

| 适配器 | v1 桩行为 | 将来实现 |
|---|---|---|
| `PaymentAdapter`（支付） | 下单提交后**同步回调**：直接置订单「已支付」并触发状态机（记 `pay_time`），不真正调起微信支付 | 微信支付 V3 下单 + 异步回调 |
| `RefundAdapter`（退款） | 直接写 `fin_refund_ledger` 一条 `status = 成功` 的记录，不实际退款 | 微信原路退回 |
| `WaybillAdapter`（电子面单） | 返回规则化假单号（如 `SF` + 时间戳） | 快递100 / 菜鸟 |
| `ProductionAdapter`（生产/MES） | `ManualProductionAdapter`：仓管手工录工单号、手工推进状态 | `MesProductionAdapter`：调 MES API |

**图片机器审核**亦为外部依赖：v1 桩**恒返回「通过」**，仅保留 pHash 黑名单的真实比对（见 `05` 篇 §2.1）。

> **桩只替换「与外部通信」那一层**。状态机、幂等、快照、流水等业务逻辑在桩与真实实现之间**完全一致**——这是「迁移时业务代码不动」的前提。
