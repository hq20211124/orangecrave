# 08 — 演示数据构造说明（demo.sql）

`orangecrave-admin/sql/demo.sql` 不是随机造数脚本，而是**按时间顺序写的一篇运营流水账**：
从开张前夜配置活动，到第一周接单、发货、售后、侵权驳回，再到当天早上还没处理完的待办。
读完这个脚本，等于读完一遍系统业务逻辑。

## 1. 为什么用「剧情」而不是「随机数据」

随机数据能填满表格，但填不出下面这些东西，而它们恰恰是演示和验收的重点：

- **状态机是否连贯**：`oms_order_status_log` 必须能从 0 一路走到终态，且每一步有人（user / system / factory / admin）、有时间、有理由
- **跨表是否自洽**：订单有售后，账上就该有退款流水；订单发了货，就该有物流单；订单进了车间，就该有 MES 工单号
- **数字是否对得上**：看板月销 = 各订单实付之和；日结 = 当日支付 - 当日退款；退款流水总额 = 售后金额
- **待办是否可操作**：运营登录进来必须"有活干"，而不是所有单都完结、所有工单都关闭

所以脚本里的每一笔金额、每一个时间戳都是互相咬合的，改一处就要连带改另一处（第 6 节有对账方法）。

## 2. 时间锚点

- 全部时间锚定在 **2026-10-15 ~ 2026-10-22**，其中 **10-22 是"今天"**
- 脚本里出现的"今早""凌晨 1 点"都是相对 10-22 说的
- 当前状态（待付款 / 待审核 / 待发货 / 待处理工单）全部落在 10-22，其余状态落在之前几天
- 判据：`pay_time >= CURDATE()` 的单量就是"今日单量"，脚本里只有订单 8（凌晨 1 点）命中，所以看板"今日销售 9.20"是合理的

**时间会漂移**：过了 10-22，看板的"今日""本月"就会变。演示期换日期时，按第 6 节的脚本整体平移，不要只手改几行。

## 4. 十三幕（脚本顺序 = 业务发生顺序）

| 幕 | 内容 | 关键表 |
|---|---|---|
| 第零幕 | 补齐商品目录（手机壳、钥匙扣），否则订单 JOIN 不到 SPU | `pms_spu/sku/sku_craft` |
| 第一幕 | 开张前夜：建新人券、两场秒杀、邀请活动 | `mkt_activity/coupon` |
| 第二幕 | 第一波注册用户 + 实名认证三态 + 新人券发放 | `ums_user/identity_cert/coupon_user` |
| 第三幕 | 第一周订单：秒杀单、进货单、团购单、驳回单、超时单、大单、分享码单 | `oms_order/item/image/status_log/delivery` |
| 第四幕 | 售后与客服：印糊退款、色差驳回、物流咨询、色差投诉、代建工单 | `oms_aftersale`、`svc_ticket/reply` |
| 第五幕 | 作品与分享：9 个作品（正常/待审/违规）、版权承诺、分享码 | `wms_work`、`aud_copyright_promise`、`wms_share_code` |
| 第七幕 | 生产工单（MES 号挂在 `oms_order` 上）与发票四态 | `oms_order.work_order_no`、`oms_invoice` |
| 第八幕 | 当天还没处理完的事：待付款、待发货、打样单、待审售后、待受理工单、合集、邀请记录、黑名单、失效分享码、延迟任务、地址簿、退款流水、日结 | 见下 |

> 脚本里没有"第六幕"编号，是因为发票与工单被并入第七幕，场景叙述不受影响。

第八幕是本次补齐的重点——它把原来"全是完结态"的演示补成了"运营早上打开后台有活干"：

- 待付款 1 单、待审核 1 单、待生产 1 单（打样）、生产中 1 单、待发货 1 单、已发货 1 单
- 待审售后 1 条（少发 5 张）、待受理工单 1 条、待审认证 1 条
- 财务：3 笔已退 + 1 笔强制退款待复核 + 5 天日结
- 审核：黑名单 2 条（含 pHash）、失效分享码 1 条
- 营销：邀请记录 2 条（1 条已奖励、1 条未转化）
- 任务：延迟任务 4 条（待执行 2、成功 1、失败 1）
- 用户：地址簿 3 条（小程序下单不用手填）

## 5. 关键口径（容易写错的几处）

| 口径 | 规则 | 脚本里的体现 |
|---|---|---|
| 订单状态码 | 0 待付款 / 2 已支付待审 / 3 待生产 / 4 生产中 / 5 质检 / 6 待发货 / 7 已发货 / 8 已完成 / 9 已取消 | `oms_order_status_log` 逐跳记录，**不跳级** |
| 审核驳回 | 驳回即取消并退款，用户需重新下单（不支持原地改图） | 订单 10 驳回 → 订单 4 重下 |
| 打样单 | `order_type = 2`，**不进销售口径**（看板 SQL 排除） | 订单 11，85 元 |
| 团购单 | `group_id` 挂 `mkt_group`，成团后按团价结算 | 订单 3，300 张 × 8.5 |
| 分享码单 | `order_type = 3`，付款方≠收货方 | 订单 9，9.2 元 |
| 作品状态 | 1 正常 / 2 待审核 / 3 待修改 / 7 违规 | 作品 5 待审、作品 7 违规 |
| 退款 | 成功退款写 `fin_refund_ledger`；待复核 `status=1, review_status=1` | 4 笔，3 成功 1 待复核 |
| 日结 | 普通单按支付口径、团购单按成团口径、退款单列 | 5 天，10-22 当天还没跑 |

## 6. 怎么验证 / 怎么重跑

**重跑**（幂等，开头会先 DELETE 所有业务表，不碰 `sys_*` 与商品基础数据）：

```bash
mysql -uroot -p orangecrave < orangecrave-admin/sql/demo.sql
```

**核对**（数字必须与脚本末尾"数据汇总"一致）：

```sql
SELECT COUNT(*) FROM ums_user;                 -- 12
SELECT COUNT(*) FROM oms_order;                -- 13
SELECT status, COUNT(*) FROM oms_order GROUP BY status;
SELECT COALESCE(SUM(pay_amount),0) FROM oms_order
  WHERE deleted=0 AND order_type<>2 AND pay_time IS NOT NULL;   -- 3659.00
SELECT COUNT(*) FROM svc_ticket WHERE deleted=0 AND status IN (1,2);  -- 1 待处理
```

**界面核对**：登录后台 → 经营看板（月销 3659 / 今日 9.20）→ 运营待办（7 个数字都有值）→ 订单（13 单 8 种状态）→ 售后（待审 1）→ 工单（待受理 1）→ 审核（待审 1 + 黑名单 2）→ 财务（日结 5 行、退款 4 行）→ 营销（活动 3 / 团 1 / 券 12 / 邀请 2）。

## 7. 已知边界

- **小程序端看不到这些数据**：`/client-api/auth/wx-login` 仍是桩，mock openid 登录后是新用户，订单/作品/券都为空。要演示小程序端，需把登录桩改为按 openid 查 `ums_user`（属于代码改动，不在 SQL 范围）。
- **日期会过期**：锚点是 10-22，跨月后"本月销售"归零、趋势图变空。
- **图片是占位域名**：`api.trae.cn/mock/...` 不保证可访问，只保证字段非空、结构正确。
- **不模拟并发/中间状态**：秒杀库存、锁、队列这些运行时行为脚本造不出来，靠 k6 压测脚本验证。
