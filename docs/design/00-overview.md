## 4. 认证与权限

### 4.1 认证

后台认证采用 Sa-Token，但**对外请求头与顾客端保持一致**：

```
Authorization: Bearer <token>
```

Sa-Token 通过 `SaTokenConfig` 自定义 token 读取名，改为从 `Authorization` 头取 `Bearer` 后的值。

认证层抽 `AuthProvider` 接口，v1 实现为「后台自建账号密码」，为将来接企业微信/钉钉 SSO 留位。

**统一响应信封**（与顾客端一致）：

```json
{ "code": 0, "msg": "success", "data": {} }
```

`code === 0` 为成功；`401` 触发前端重新登录。**注意**：顾客端还有 `code === 1000` 表示刷新 token，后台 v1 不需要，但保留该错误码语义避免冲突。

### 4.2 权限模型

**菜单级 + 按钮级**两级：【推断：依据敏感操作分布判断必需】

- **菜单级**：角色决定能进入哪些页面
- **按钮级**：同一页面内的敏感操作单独控权

必须单独控权的操作（这些和查看类操作同页共存，只做菜单级挡不住误操作）：

| 操作 | 说明 |
|---|---|
| 强制退款 | 绕过正常流程退款 |
| 修改价格 | 改 SKU 价格 / 活动价 |
| 审核放行 / 驳回 | 定制图与作品的审核结论 |
| 手工改订单状态 | 绕过状态机强制推进 |
| 发放优惠券 / 打样券 | 涉及成本 |

### 4.3 内置角色

| 角色 | 职责 | 关键权限 |
|---|---|---|
| 超级管理员 | 全部 | 含系统配置 |
| 客服 | 订单查询、工单处理、售后 | 看订单；**不能**强制退款、不能改价 |
| 仓管 | 生产状态推进、发货 | 改进度、发货；不能改价 |
| 运营 | 商品、活动、优惠券 | 全部营销权限 |
| 审核 | 定制图与作品审核 | 审核结论；不能动订单金额 |
| 财务 | 对账、退款复核 | 看流水、导出；强制退款需复核 |

## 5. 延迟任务方案

系统里有大量「到点触发」的动作：

| 任务 | 超时 | 动作 |
|---|---|---|
| 待付款订单 | 30 分钟（可配） | 取消订单 + 还库存 + 返优惠券 |
| 拼团未成团 | 24 小时 | 拼团失败 + 自动退款 |
| 付款后退款窗口 | 4 小时 | 关闭退款入口 |
| 分享码到期 | 可配 | 失效 + 退未核销预付款 |
| 作品过期 | 可配 | 状态转「作品过期」 |
| 待收货 | 10 天（可配） | 自动确认收货 |
| 优惠券到期 | 各自配置 | 失效 |

### 5.1 为什么不用 `@Scheduled` 扫描

- 有最多 60 秒的延迟误差
- 全表轮询，随订单表增长而变慢

### 5.3 本设计的选择：三层

```
① DelayQueue        精准计时，任务到点即触发
② 启动重建            ApplicationRunner 扫库重建，解决重启丢任务
③ 低频兜底扫描        @Scheduled 每 5 分钟，补静默丢失的任务
```

**可靠性契约**：每新增一类延迟任务，必须同时提供 ① 注册点 ③ 兜底扫描查询。二者缺一，该类任务就不具备可恢复性。

绝不「先查再改」。统一用**带状态条件的 UPDATE 并检查影响行数**：

```sql
UPDATE `order` SET status = '已取消', cancel_time = NOW()
WHERE id = ? AND status = '待付款';
-- 影响行数 == 1 才说明本次调用赢得了竞争
```

- **重复取消**：第二次匹配 0 行，自然无操作
- **取消 vs 支付回调竞态**：支付回调执行 `UPDATE ... SET status='已支付' WHERE id=? AND status='待付款'`，先提交者赢；输的一方拿到 0 行，走退款或放弃分支
- **状态机本身就是并发控制**，无需额外行锁

### 5.5 迁移路径

| 规模 | 方案 | 变更点 |
|---|---|---|
| 本机 / 单实例 | DelayQueue + 重建 + 兜底 | 本设计 |
| 多实例 | 换 xxl-job 触发扫描 | 扫描体不变，加分布式锁 |
| 高 QPS | RabbitMQ TTL+DLX / RocketMQ 延迟消息 | 消费端条件 UPDATE 逻辑原样搬 |

**关键**：状态机与幂等逻辑在三档之间**不变**，只是触发方式换了。

**已就位的一档**：`DistributedLock` 抽象已落地——进程内实现（单 JVM 互斥）与 Redis 实现（`SET NX PX` + 持有者令牌）由 `orangecrave.redis.enabled` 切换，`DelayTaskEngine.scan()` 与幂等清理任务都走它。因此**多实例部署现在只需打开开关**，扫描体一行不改；将来换 xxl-job 时这把锁仍复用。

## 6. 工程结构

```
orangecrave-admin/
├─ orangecrave-common/        通用：响应体、异常、工具、常量
├─ orangecrave-system/        系统管理：账号/角色/菜单/日志/参数配置
├─ orangecrave-user/          用户：小程序用户、地址、身份认证
├─ orangecrave-goods/         商品：系列/品类/SPU/SKU/画师
├─ orangecrave-work/          作品：作品、合集、分享码、打样
├─ orangecrave-order/         订单：订单、状态机、生产、发货、售后、发票
├─ orangecrave-audit/         审核：定制图、作品 UGC、侵权
├─ orangecrave-marketing/     营销：活动骨架、拼团、秒杀、优惠券
├─ orangecrave-service/       客服工单
├─ orangecrave-finance/       财务：对账、看板
├─ orangecrave-task/          延迟任务：DelayQueue、重建器、兜底扫描
├─ orangecrave-admin-api/     后台接口入口（启动模块）
└─ orangecrave-admin-web/     原生 HTML/JS 前端（静态资源）
```

**分层约定**（每个业务模块内部一致）：

```
controller/   仅做参数校验与响应封装
service/      业务逻辑，事务边界在此
mapper/       MyBatis-Plus Mapper
domain/       实体（对应表）
dto/          入参
vo/           出参
convert/      domain ↔ dto/vo 转换
```

## 8. 与顾客端接口的关系

本后台是**独立系统**，与顾客端接口**不共用数据库、不互相调用**。

但**对外风格统一**（见 4.1），使前端请求封装与错误处理可共用。

> 顾客端现有 **220 个端点**，其中 125 个在当前客户端版本中未被调用——说明服务端接口为**多端共用**，其能力比小程序露出的更多。本后台不依赖这些端点。

## 9. 外部依赖与桩契约

支付、退款、电子面单、生产（MES）、图片机器审核均抽适配器，v1 走桩。**桩的行为契约见 `03` 篇第 10 节**——桩只替换「与外部通信」那一层，业务逻辑不变。

| 依赖 | 适配器 | v1 |
|---|---|---|
| 支付 | `PaymentAdapter` | 桩：同步置「已支付」 |
| 退款 | `RefundAdapter` | 桩：直接写成功流水 |
| 电子面单 | `WaybillAdapter` | 桩：假单号 |
| 生产 | `ProductionAdapter` | 桩：手工录入/推进 |
| 图片机器审核 | 远程 pipeline | 桩：恒通过（pHash 真实比对） |
