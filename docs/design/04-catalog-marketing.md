# 04 · 商品计价与营销

> 表结构见 `01-database.md` 第 3、7 节。本篇讲**业务规则与算法**，不重复字段定义。

## 1. 商品组织

```
系列/IP主题 → 品类 → SPU → SKU
```

### 1.1 为什么要「系列」这一层

「千款原创联名产品」意味着商品量大且以 **IP 主题**为组织维度。若只有「品类」一层，「千款联名」在后台就是一堆平铺商品：

- 运营**无法按系列上下架**（如某番联名到期需整体下架）
- 无法**按系列统计销量**（而这是运营最需要的视角）
- 用户在小程序按 IP 找货，后台却没有对应结构

加一层成本极低，收益明确。

### 1.2 品类示例

小卡 / 卡册 / 手机壳 / 卡套 / 笔记本 / 亚克力 / 照片集 / NFC音乐卡 / 拍立得挂件

## 2. 计价模型

### 2.1 三种计价方式

| `pricing_type` | 方式 | 适用 | 公式 |
|---|---|---|---|
| 1 | **按张** | 小卡、卡套 | `单价 × 数量` |
| 2 | **按面积** | 亚克力、相框 | `面积(长×宽) × 每平米单价 × 数量` |
| 3 | **数量阶梯** | 批量印刷 | `阶梯单价(数量) × 数量` |

**必须在商品维度可选**。理由：你们既有按张卖的小卡，也有按面积卖的亚克力——硬统一成一种算法，必有一类算错。

### 2.2 完整计价流程

```
基础价（按 pricing_type 算出）
  + 工艺加价（白墨/烫金/覆膜，固定额或按面积）
  + 材质加价（亚克力/板材）
  × 规格系数
  ─ 活动折扣（拼团价 / 秒杀价 / 优惠券）
  = 商品金额
  + 运费（按模板，满额减免）
  = 应付金额
```

### 2.3 起订量与递增量

- `min_order_qty` —— 低于此数不能下单
- `increment_qty` —— 必须是此数的整数倍

规则结论（校验点，提示文案自拟）：

- 删除商品时需提示其起订量。【待定：后台当前没有删除商品入口（下架经商品编辑页切状态实现），该规则暂无触发点；待产品确认是否提供删除入口，若提供再补「入口 + 起订量提示」】
- 保存/下单前校验是否达到起订量，未达标要说明还差多少。
- 数量同时受起订量与递增量两重校验。

> 这条同样约束**无料分享**：未达起订量的作品不能发起无料分享

### 2.4 工艺

| 工艺 | 加价方式 |
|---|---|
| 白墨 | 按面积 |
| 烫金 | 固定 / 按面积 |
| 覆膜 | 按面积 |
| 板材 | 规格加价 |

工艺从 SKU 带出，**进入生产工单的工序清单**。

### 2.5 价格快照

下单瞬间固化 `unit_price` / `craft_snapshot` / `pricing_snapshot`。SKU 改价**不影响历史订单**。

### 2.6 面积计费的实现注意

面积按 **SKU 的物理尺寸**（长 × 宽，单位 mm）计算，非图片像素。

```
面积(m²) = (长mm / 1000) × (宽mm / 1000)
```

精度：面积保留 4 位小数，金额保留 2 位。

## 3. 营销活动

### 3.1 共用骨架

拼团、秒杀、优惠券、邀请好友**共用 `mkt_activity` 表**，靠 `activity_type` 区分，各自规则存 `rule_config` (json)。

**为什么共用**：四者的生命周期、时间窗、启停、商品绑定逻辑完全一致，只有「规则内容」不同。分四张表会导致四套几乎相同的 CRUD。将来加「满减」「套餐」也只是加一个 `activity_type`。

### 3.2 拼团

**规则**：满 3 人付款后才进入制作；不足 3 人视为拼团失败，24 小时后自动退款。

| 参数 | 默认 | 可配 |
|---|---|---|
| 成团人数 | **3** | 是 |
| 成团时限 | **24 小时** | 是 |
| 模拟成团 | **关闭** | 是（开关） |
| 拼团价 | 活动维度独立价 | 是 |

**关键设计点**：

1. **拼团价是活动维度的独立价**，不改 SKU 原价；下单时记录成团价快照
2. **拼团价与优惠券互斥** —— 拼团已让利，再叠券击穿成本，且规则复杂用户算不清
3. **成团判定与退款必须走条件 UPDATE** —— 第 3 人支付与 24h 到期任务可能同时触发
4. **模拟成团做成开关，默认关闭** —— 涉及「假装有用户」，需业务方确认合规性

**成团后的处理**：团内所有成员订单从「待成团」批量转「待审核」（各自走审核与生产）。

**失败后的处理**：所有成员订单转「已取消」+ 各自退款（写 `fin_refund_ledger`，`biz_type = 2`）。

### 3.3 秒杀

| 参数 | 说明 |
|---|---|
| 秒杀价 | 独立价 |
| 秒杀库存 | 独立配额，不占 SKU 库存 |
| 每人限购 | 防刷 |
| 场次 | 按时间段开抢 |

**库存扣减**：秒杀走**独立库存**，与 SKU 库存分离，避免秒杀掉量影响正常售卖。

**预扣机制**（03 篇 §2.6 的库存侧细节）：

秒杀下单的库存保护分两层：

```
请求 → StockGate 预扣（内存/Redis，原子判余量+扣数）
         ↓ 通过
       DB 条件 UPDATE（兜底，防闸门与库不一致）
         ↓ 返回 0（DB 也没货了）
       StockGate.restore()（归还预扣）
```

| 层 | 组件 | 说明 |
|---|---|---|
| 闸门层 | `StockGate`（`NoopStockGate` / `RedisStockGate`） | Lua 原子读配额+判余量+扣数，Redis 实现带 TTL 防泄漏 |
| 兜底层 | DB `UPDATE ... WHERE stock >= ?` | 条件更新，防闸门与库不一致 |
| 归还 | `StockGate.restore()` | 闸门过了但 DB 扣 0 时必须归还，否则超卖 |

**失败方向**：闸门预扣不随建单事务回滚（事务在 DB 层，闸门在 Redis/内存层）。方向是「少卖」而非「超卖」，账本以 DB 为准。

### 3.4 优惠券

| 类型 | 说明 |
|---|---|
| 满减 | 满 X 减 Y |
| 折扣 | 打 N 折 |
| 无门槛 | 直接减 |

**发放方式**（三种都做）：

| 方式 | v1 |
|---|---|
| 人工发放（定向） | ✅ |
| 自动发放（新人/活动） | ✅ |
| 领券中心（用户自领） | 属顾客端页面，**留接口位** |

**互斥规则**：与拼团价互斥。

**核销**：券在订单提交时锁定，支付成功后核销，取消/退款时**返还**（开源电商项目 在此处的实现可参照：取消订单时会 `releaseCoupon`）。

### 3.5 邀请好友

| 参数 | 说明 |
|---|---|
| 被邀请人奖励 | 通常为券 |
| 邀请人奖励 | 券 / 积分 |
| 上限 | 防刷 |

### 3.6 渠道归因

订单上记 `channel_id`，用于统计「哪个平台值得投」。**只做归因，不做完整渠道管理**（佣金、专属链接）——那是另一套体系。

## 4. 优惠计算顺序

**顺序必须固定**，否则同一单在不同页面算出不同金额：

```
1. 活动价（拼团价 / 秒杀价）覆盖原价     ← 与优惠券互斥
2. 优惠券抵扣                          ← 仅在无活动价时生效
3. 满额包邮判定                        ← 用「商品金额」判定，非实付
4. 运费模板计算
```

**满额包邮的判定基数用商品金额**（券前），否则用券会导致刚好掉出包邮门槛。

> 现有规则：满 28 元减 4 元运费。

## 5. 库存策略

| 商品类型 | 扣减时机 | 释放时机 |
|---|---|---|
| **定制品** | **不占 SKU 库存** | — |
| **现货** | 下单即扣 | 取消/超时 → 归还 |
| **拼团** | **不占库存**，按成团人数判定 | 失败 → 退款 |
| **秒杀** | 秒杀独立库存，下单即扣 | 取消 → 归还 |

**为什么定制品不占库存**：定制品是「来一张图印一张」，不存在成品库存积压；真正占的是原材料（纸、墨），v1 不做原材料核算。

**归还库存必须与取消在同一事务内**，并走条件 UPDATE 保证幂等。

## 6. 画师（只做归属，不做分成）

| 做 | 不做 |
|---|---|
| 商品标记画师 | 按比例分成计算 |
| 统计某画师作品销量 | 月度结算单 |
| 按画师筛选商品 | 提现流程 |

**理由**：分成规则各家合同不同（按售价百分比 / 按张 / 买断价），硬编进系统既不通用、又极易算错引发纠纷。v1 把**归属和销量**做准，出账线下用 Excel。

字段位留好，将来要做自动化结算不用改表。

## 7. 商品管理中的敏感操作

以下操作**必须记录改前/改后快照**：

| 操作 | 权限标识 |
|---|---|
| 修改 SKU 价格 | `goods:price:update` |
| 批量改价 | `goods:price:batch` |
| 修改库存 | `goods:stock:update` |
| 上下架 | `goods:status:update` |
| 修改活动规则 | `marketing:activity:update` |

**理由**：后台改价直接影响收入，出事时要能回答「这个价是谁改的、原来是多少」。
